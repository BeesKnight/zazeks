# Стратегия развёртывания и исполнения

## 1. Режим работы: гибрид (онлайн + офлайн)

Мы выбираем гибридный режим, в котором:

- **Базовый геймплей и распознавание жестов выполняются локально** на пользовательском устройстве с помощью оптимизированной TFLite-модели. Это даёт минимальную задержку, работает даже при нестабильном соединении и не требует отправки изображений рук на сервер.
- **Серверная часть остаётся активной** для функций, которые принципиально завязаны на сетевое взаимодействие: мультиплеер по WebSocket, хранение профилей и статистики, лидерборды, администрирование, а также отложенная аналитика качества распознавания. Сервер также выступает в роли поставщика обновлённых весов модели и фронтенда.

Такой баланс даёт:

1. **Приватность и низкие задержки** при распознавании жестов (видеокадры не покидают устройство).
2. **Возможность общей игры и синхронизации данных** через существующие REST/WebSocket API.
3. **Упрощённое обновление модели**: новые веса доставляются с сервера и обновляются в локальном кэше, без необходимости пересобирать клиентское приложение.

### 2.2 WebSocket

- `GET /ws/multiplayer` — вход в очередь матчмейкинга. Клиент после подключения отправляет `{ "action": "join", "user_id": str }`. Далее используются события `ready`, `gesture`, `play_again`, `signal`. Авторизация проводится на уровне предварительной REST-валидации и передачи проверенного `user_id` + HMAC-подпись (см. требования безопасности ниже).

### 2.3 Требования к безопасности

1. **JWT-аутентификация:**
   - Использовать `Authorization: Bearer <token>` для всех защищённых REST-эндпоинтов.
   - Access token живёт `ACCESS_TOKEN_EXPIRE_MINUTES`, затем требуется обновление.
2. **Пароли:** хешируются через `bcrypt` (см. `src/security.py`); пароли и логины проходят валидацию по regex.
3. **Хранение и передача изображений:** разрешены только JPEG/PNG до 5 МБ. При загрузке проверяется формат и размер (см. `/user/{id}` PUT).
4. **Защита WebSocket:**
   - Перед установлением WebSocket-сессии клиент получает JWT и формирует подпись `{user_id, nonce}` (HMAC-SHA256 по `SECRET_KEY`). Сервер проверяет подпись в первом сообщении `join`, иначе закрывает соединение.
   - Лимитировать количество параллельных сессий per user и вводить тайм-ауты бездействия.
5. **Серверная инфраструктура:**
   - Включить CORS только для доверенных доменов на production.
   - Логировать подозрительные действия (многократные попытки регистрации, невалидные токены).
   - Везде использовать HTTPS.
6. **Модель как сервис:** если включается `/model/detect`, ограничивать размер файлов и частоту запросов (rate limiting), а также изолировать процесс инференса для предотвращения RCE через OpenCV.

## 3. Офлайн-пайплайн модели (TFLite)

### 3.1 Целевой формат

- **TFLite float16** (динамик диапазон) — оптимален для мобильных и десктопных CPU, сохраняет точность YOLOv8/YOLOv11 при значительном уменьшении размера.

### 3.2 Подготовка модели

1. **Экспорт весов из обученной модели** (`best.pt` лежит в `backend/src/api/best.pt`).
2. **Конвертация в ONNX:**
   ```bash
   yolo export model=backend/src/api/best.pt format=onnx imgsz=224
   ```
3. **Преобразование в TFLite** через `onnx-tf` и TensorFlow Lite Converter:
   ```bash
   onnx-tf convert -i best.onnx -o best_saved_model
   python - <<'PY'
   import tensorflow as tf
   converter = tf.lite.TFLiteConverter.from_saved_model("best_saved_model")
   converter.optimizations = [tf.lite.Optimize.DEFAULT]
   converter.target_spec.supported_types = [tf.float16]
   tflite_model = converter.convert()
   with open("best_fp16.tflite", "wb") as f:
       f.write(tflite_model)
   PY
   ```
4. **Постобработка:** упаковать `best_fp16.tflite` и `label_map.json` (отображение классов `{"0": "Paper", "1": "Rock", "2": "Scissors"}`) в пакет обновления.

### 3.3 Доставка и загрузка на клиенте

1. **Версионирование**: сервер хранит манифест `/model/manifest.json` c полями `{ "version": "2025.03.01", "url": "https://.../best_fp16.tflite", "sha256": "..." }`.
2. **Клиент при запуске** проверяет локальную версию в IndexedDB/LocalStorage. Если версия устарела — скачивает новую модель фоново.
3. **Валидация целостности**: после загрузки сверяется SHA-256 и только затем модель переопределяет предыдущую.
4. **Инициализация**: модель загружается через `@tensorflow/tfjs-tflite` или через `TensorFlow Lite Web` (для браузера) / `tflite_runtime` (для Python desktop). Сессия инференса использует локальный видеопоток, и выдаёт предсказания с частотой 5–10 FPS для стабильного UX.

## 4. Стратегии офлайн-работы

1. **Кэширование модели и ассетов**
   - PWA Service Worker кэширует `best_fp16.tflite`, label map и ключевые бандлы, чтобы офлайн-режим продолжал работать.
   - В десктопном и Android-приложении веса и конфигурация сохраняются в локальном каталоге (`%APPDATA%/Zazeks/models`, `context.filesDir/models`). Версия хранится в SharedPreferences/LocalStorage.

2. **Локальные сценарии геймплея**
   - Игры против бота и режим тренировки не требуют сети: инференс выполняется локально, результаты сохраняются в SQLite/Room.
   - Пользовательские профили кэшируются и доступны только для чтения до следующей синхронизации.

3. **Graceful degradation инференса**
   - Если локальный запуск TFLite не удался (например, неподдерживаемый браузер), клиент переключается на облачный эндпоинт `/model/detect`. Вся передача ведётся через HTTPS, изображения ограничены по размеру и удаляются после обработки.
   - При сетевой ошибке повторяем запрос с экспоненциальной задержкой до 3 раз, затем возвращаем управление офлайн-игре с текстом «Распознавание недоступно, используйте выбор жеста вручную».

4. **Синхронизация статистики**
   - Результаты офлайн-игр пишутся в локальный IndexedDB/Room кэш. Сервис-воркер или WorkManager периодически пытается отправить пачками через `POST /game/`. При неудаче данные остаются локально, и UI отображает пометку «не синхронизировано».
   - После успешной синхронизации локальные записи помечаются как отправленные, чтобы избежать дублей (дублируется логика на сервере — 10-секундный дубликат чекер).

5. **WebSocket fallback**
   - Если мультиплеер недоступен, UI предлагает «играть против бота» и скрывает элементы живого матча. Кнопка «Повторить подключение» запускает повторный handshake.

6. **Обновление модели и ассетов**
   - При неудачном скачивании обновления клиент продолжает использовать предыдущую версию и откладывает повторную попытку на 24 часа.
   - Для критических обновлений сервер может пометить версию как `required`, тогда клиент принудительно показывает предупреждение и блокирует сетевой функционал, пока не получит свежие данные.

Такой подход обеспечивает отказоустойчивость, приватность и возможность постепенного наращивания функциональности без прерывания основного геймплея.

## 5. Логирование и аналитика

1. **Клиентские логи**
   - Android: `Timber` + `Logcat` с буферизацией в `Room`; при появлении сети батч логов отправляется на backend (`POST /logs/mobile`).
   - Веб: `console`-события и ошибки JavaScript собираются через `Sentry` SDK, офлайн-события складываются в IndexedDB.

2. **Серверные логи**
   - Backend (FastAPI) пишет структурированные логи в JSON (`structlog`/`loguru`), проксируемые в `Loki`/`ELK`. Для WebSocket-сессий логируются handshake, ошибки, аномальные отключения.
   - Модельный сервис (`onnxruntime`/`tflite`) пишет отдельный канал для мониторинга latency.

3. **Метрики и аналитика**
   - Счётчики Prometheus: latency API, число активных игроков, успешность распознавания, процент офлайн-сессий.
   - Событийная аналитика (Amplitude/Matomo): начало игры, завершение, переключение между офлайн/онлайн режимами, использование подсказок.
   - ML-метрики (precision/recall) публикуются в MLflow, nightly-джобы обновляют графики деградации качества.

4. **Политики хранения и приватность**
   - Логи с биометрическими данными (изображения) не отправляются — фиксируются только агрегированные результаты инференса.
   - Все пользовательские идентификаторы псевдонимизируются перед отправкой в аналитические системы.
   - Срок хранения логов по умолчанию 30 дней, расширенный retention согласуется с требованиями безопасности.

5. **Оповещение и реагирование**
   - Настраиваются алерты в Grafana/Prometheus по SLA (ошибки 5xx > 2%, задержка распознавания > 500 мс, рост офлайн-очереди).
   - DevOps/QA дежурные получают уведомления в Slack/Telegram, формируются инцидентные отчёты.
